# Package com.lightningkite.lightningserver.terraform

Infrastructure-as-Code integration for Lightning Server deployments using Terraform.

## Overview

This package provides the core abstractions for generating and managing Terraform configurations
for Lightning Server deployments. It handles:

- Terraform JSON file generation from server configurations
- Secret management with multiple backend support
- Interactive deployment workflows
- Integration with service implementations for infrastructure provisioning

## Main Components

### BaseTerraformEmitter.kt

**`BaseTerraformEmitter<S : ServerBuilder>`**
Abstract base class for Terraform configuration generation.

Key responsibilities:

- Coordinates Terraform file generation from server settings
- Manages provider requirements and variables
- Provides deployment workflows (init, plan, apply)
- Handles secret retrieval and environment preparation

Key methods:

- `write()`: Generate .tf.json files in terraformRoot
- `deploy()`: Full deployment workflow with confirmation
- `editVars()`: Interactive secret editor
- `terraform(vararg command)`: Execute terraform commands
- `prepareTerraform()`: Prepare environment variables for Terraform

Implementations must provide:

- `builder`: The ServerBuilder instance to deploy
- `secretsSource`: Source for retrieving secrets
- `terraformRoot`: Directory for generated Terraform files
- `settings()`: Extension function to configure server services

**`Deployment`**
Simple interface for objects that can perform deployment operations.

**Context function: `TerraformNeed<SecretBasis>.generated()`**
Configures a SecretBasis to be auto-generated by Terraform using a random password resource.

### SecretSource.kt

Interfaces and implementations for managing deployment secrets.

#### Core Interfaces

**`SecretSource`**
Base interface for retrieving secrets.

- `name`: Display name for this source
- `getOrNull(need)`: Retrieve a secret, or null if not found
- `get(need)`: Retrieve a secret, throwing if not found

**`InteractiveSecretSource`**
Secret source that can prompt users for missing values.

- `prompt(need)`: Interactively prompt for a secret value

**`PopulatableSecretSource`**
Secret source that can both retrieve and store secrets.

- `set(need, value)`: Store a secret value
- Implements `get()` to prompt and store if value not found

#### Implementations

**`EnvironmentSecretSource`** (object)
Reads secrets from environment variables with `LS_SECRET_` prefix.
Example: `LS_SECRET_AWS_ACCESS_KEY_ID` for the AWS_ACCESS_KEY_ID secret.

**`EncryptedFileSecretSource`**
Stores secrets in an AES-256 encrypted JSON file, protected by a password.

Constructor:

- `EncryptedFileSecretSource(file, name, passwordFetcher)`: Explicit file location
- `EncryptedFileSecretSource(name)`: Uses ~/.lightningserver/{name}.json.enc

Security Features (Version 2):

- AES-256-CBC encryption
- PBKDF2-HMAC-SHA256 key derivation (100,000 iterations)
- Random 32-byte salt per file
- Automatic migration from legacy format (version 1)

Suitable for local development and testing. For production, consider dedicated secret managers.

**`ManySecretSources`**
Chains multiple secret sources with fallback behavior. Returns the first non-null value
when retrieving, and prompts for storage location when setting new values.

**`PasswordFetcher`**
Helper for prompting and caching password input. Caches the password in memory after
first entry to avoid repeated prompts within a session.

#### Utility Functions

**`runGuiEditor(variables)`** (Extension on SecretSource)
Opens a Swing-based GUI for viewing and editing secrets.

**`runTerminalEditor(variables)`** (Extension on SecretSource)
Opens a terminal-based interactive menu for managing secrets.

## Usage Patterns

### Basic Deployment Configuration

```kotlin
object MyDeployment : BaseTerraformEmitter<MyServer>() {
    override val builder = MyServer
    override val terraformRoot = File("terraform/prod")
    override val secretsSource = EncryptedFileSecretSource("production")

    override fun MyServer.settings() {
        database.direct(DatabaseSettings())
        // ... configure other services
    }
}
```

### Multi-Source Secret Management

```kotlin
val secrets = ManySecretSources(
    EnvironmentSecretSource,              // Try env vars first
    EncryptedFileSecretSource("production"), // Fall back to encrypted file
)
```

### Interactive Secret Setup

```kotlin
fun main() {
    MyDeployment.editVars()  // Opens interactive editor
}
```

### Automated Deployment

```kotlin
fun main() {
    MyDeployment.deploy()  // Runs terraform init/plan/apply workflow
}
```

## Design Principles

1. **Separation of Configuration and Secrets**: Infrastructure configuration is versioned
   in code, while secrets are managed separately through SecretSource implementations.

2. **Progressive Enhancement**: Basic deployment works with minimal configuration, but
   advanced users can customize Terraform generation, add custom resources, and implement
   custom secret sources.

3. **Interactive Fallbacks**: When secrets are missing, the system prompts interactively
   rather than failing immediately, making initial setup smooth.

4. **Multi-Environment Support**: By using different terraformRoot directories and secret
   sources, the same code can deploy to multiple environments.

## Known Limitations

1. **Terraform Binary Required**: Must have `terraform` command available on PATH (or set via
   `TERRAFORM_BINARY` environment variable).

2. **Interactive Prompts**: Some operations (password entry, confirmation prompts) require
   interactive terminal or GUI access, which may not work in all CI/CD environments.

3. **Shell Argument Parsing**: `terraformShell()` splits commands on spaces and doesn't
   handle quoted arguments correctly.

4. **Password Memory**: PasswordFetcher stores passwords as String in memory, which cannot
   be securely zeroed. Consider this when working with highly sensitive deployments.
