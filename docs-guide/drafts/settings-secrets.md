# Settings & Secrets

Settings are the bridge between code and configuration.  You declare what your server
needs — a database URL, a cache address, a `SecretBasis` for signing tokens — and
Lightning Server reads the values from `settings.json` at startup.  The same mechanism
also supports encrypted settings files for secrets that should never be stored in
plaintext, and AWS Secrets Manager integration for production deployments.

All examples in this chapter use the following imports:

## Declaring Settings

Call `setting("key", defaultValue)` inside your `ServerBuilder`.  The string key becomes
the field name in `settings.json`; the default value provides both the type and the
out-of-the-box value for local development.

```kotlin
// Illustrative — matches the ServerBuilder.setting() DSL.
object Server : ServerBuilder() {
    // Simple string setting.
    val webUrl = setting("webUrl", "http://localhost:8080")

    // A @Serializable data class — produces nested JSON.
    val featureFlags = setting("featureFlags", FeatureFlags())

    // Service settings follow the same pattern; the default ("ram", "local", etc.)
    // works without any external infrastructure.
    val database = setting("database", Database.Settings())
    val cache    = setting("cache",    Cache.Settings())
    val files    = setting("files",    PublicFileSystem.Settings())
}
```

Access a setting's value inside a handler or any other `ServerRuntime` context by
invoking it like a function:

```kotlin
// Illustrative — settings are callable anywhere a ServerRuntime context is present.
val rootHandler = path.get bind HttpHandler {
    val url = Server.webUrl()   // returns the String from settings.json
    HttpResponse.plainText("Serving at $url")
}
```

Settings are resolved lazily and cached for the lifetime of the runtime.  Calling
a setting at module-load time (e.g., at the top of a companion object outside a
handler) will crash because no runtime exists yet.

### Transformed Settings

`setting()` can also accept a `getter` lambda that transforms the raw JSON value into a
more useful runtime type.  The transformation runs once during the ready phase and is
cached:

```kotlin
// Illustrative — transforms a plain password string into a hashed form.
val adminPassword = setting(
    name = "adminPassword",
    default = "changeme",
    getter = { plaintext -> plaintext.bcryptHash() }
)
```

### Optional Settings

Mark a setting `optional = true` to let it be omitted from `settings.json` without
causing an error:

```kotlin
val emergencyEmail = setting("emergencyEmail", "", optional = true)
```

An optional setting that is absent from the file uses its default value.
`settings.suggested.json` will still include it as a hint to the operator.

## The settings.json Lifecycle

When `loadFromFile(KFile("settings.json"), internalSerializersModule)` is called at
startup:

1. **File does not exist** — Lightning Server writes a generated `settings.json`
   containing every declared setting at its default value, then throws
   `MissingSettingFile`.  The process exits.  Run again and the file will be read.

2. **File exists but is missing keys** — Lightning Server writes
   `settings.suggested.json` next to the original file (with all keys filled in)
   and throws `IncompleteSettingsException`.  Copy the missing lines from the suggested
   file into `settings.json` and restart.

3. **File exists and is complete** — settings are parsed, transformed, and the server
   starts normally.

This two-run startup is intentional.  The generated defaults are designed to be
functional out of the box (`"ram"` for the database, `"local"` for file storage, etc.)
so you can run the demo immediately.

```json
// Illustrative — the settings.json that Server above would generate on first run.
{
  "webUrl": "http://localhost:8080",
  "featureFlags": {
    "betaEnabled": false
  },
  "database": "ram",
  "cache": "ram",
  "files": "local",
  "secretBasis": "<auto-generated-hex>",
  "general": {
    "projectName": "My Project",
    "publicUrl": "http://localhost:8080",
    "debug": false
  }
}
```

> **Note:** service settings (`Database.Settings`, `Cache.Settings`, etc.) serialize as
> a URL string when the value matches a simple built-in backend (`"ram"`, `"local"`) or
> as a URL string with a scheme for external backends (`"mongodb://…"`,
> `"redis://…"`).  See [Services & Settings](services.md) for how to reference
> non-default backends.

## File Formats

`loadFromFile` detects the format from the file extension:

- Files with `.properties` in the name use **Java Properties format**.
- All other files use **JSON** (default).

```properties
# settings.properties — illustrative
webUrl=http://localhost:8080
database=ram
featureFlags.betaEnabled=false
```

Nested objects use dot notation in Properties files.  Both formats support the `defaults`
chaining feature described below.

## Chaining Settings Files

A JSON settings file can reference another file for base values using the special
`defaults` property:

```json
{
  "defaults": "~/shared-config.json",
  "database": "mongodb://prod-db.example.com/myapp"
}
```

Values in the main file override values from the `defaults` file.  Relative paths are
resolved relative to the parent file's directory; `~` expands to the home directory.
Multiple levels of chaining are supported; circular references are detected and reported
clearly at startup.

This is useful for sharing non-secret settings (feature flags, timeouts, log levels)
across deployment environments while keeping environment-specific values (database
URLs, external service endpoints) in the per-environment file.

## Encrypted Settings Files

When settings contain secrets — the `SecretBasis`, third-party API keys, database
passwords — you should not store them in a plaintext file.  Lightning Server can
transparently decrypt settings files at startup.

### Encrypting a File

Encrypt with OpenSSL's AES-256-CBC cipher.  Use the `-pbkdf2` flag (recommended):

```bash
openssl enc -aes-256-cbc -pbkdf2 \
    -in settings.json -out settings.json.enc
```

The legacy format (without `-pbkdf2`) is also supported for backward compatibility:

```bash
# Legacy — still accepted but not recommended for new files.
openssl enc -aes-256-cbc -md sha256 \
    -in settings.json -out settings.json.enc
```

### Decrypting at Runtime

Set the `LIGHTNING_SERVER_SETTINGS_DECRYPTION` environment variable to the encryption
password before starting the server:

```bash
export LIGHTNING_SERVER_SETTINGS_DECRYPTION="your-encryption-password"
./gradlew :server:run --args="serve"
```

Lightning Server detects the format automatically (PBKDF2 vs legacy EVP_BytesToKey) and
decrypts the file before parsing.  No code change is needed.

Point `loadFromFile` at the encrypted file:

```kotlin
// Illustrative — same call as for an unencrypted file.
// loadFromFile reads LIGHTNING_SERVER_SETTINGS_DECRYPTION and decrypts transparently.
fun main() {
    val built = Server.build()
    KtorEngine(built).apply {
        settings.loadFromFile(KFile("settings.json.enc"), internalSerializersModule)
        start(Netty)
    }
}
```

## Secrets at Deploy Time: the SecretSource Hierarchy

For deployment pipelines (Terraform generation, key rotation, provisioning scripts),
Lightning Server provides a separate `SecretSource` abstraction for reading and writing
secrets outside the normal settings-file flow.

The type hierarchy:

```
SecretSource
├── EnvironmentSecretSource      reads LS_SECRET_{NAME} env vars
├── EncryptedFileSecretSource    reads from ~/.lightningserver/{name}.json.enc
├── AwsSecretSource              reads from AWS Secrets Manager (module: secret-source-aws)
└── ManySecretSources            tries sources in order, prompts and stores if missing
```

### EnvironmentSecretSource

Reads secrets from environment variables named `LS_SECRET_{NAME}`:

```bash
export LS_SECRET_DATABASE_PASSWORD="hunter2"
```

```kotlin
// Illustrative
val db = EnvironmentSecretSource.getOrNull(dbPasswordNeed)
```

### EncryptedFileSecretSource

Stores secrets in an AES-256-CBC encrypted file under `~/.lightningserver/`.
Prompts for a password on first access (cached in memory for the session):

```kotlin
// Illustrative — file will be at ~/.lightningserver/production.json.enc
val secrets = EncryptedFileSecretSource("production")

// First call prompts for the password; subsequent calls use the cache.
val apiKey = secrets.get(myApiKeyNeed)
```

The file format uses PBKDF2-HMAC-SHA256 with 100,000 iterations and a random salt
(format version 2).  Legacy version-1 files are auto-migrated to v2 on first write.

`DynamicEncryptedFileSecretSource` is a wrapper that asks for the file path at runtime
instead of baking it in — useful when multiple developers manage different deploy
environments and you do not want to hard-code file paths in VCS.

### AwsSecretSource (secret-source-aws module)

Add the module dependency:

```kotlin
// build.gradle.kts — illustrative artifact coordinates
implementation("com.lightningkite.lightningserver:secret-source-aws:<version>")
```

Then construct `AwsSecretSource` with an AWS profile, a namespace prefix, and a region:

```kotlin
// Illustrative — constructor signature matches AwsSecretSource.kt exactly.
val awsSecrets = AwsSecretSource(
    profile = "my-aws-profile",
    idPrefix = "prod-api",            // secrets are stored as "prod-api/{name}"
    region = Region.US_EAST_1,
)

// Retrieve a value (returns null if not found, throws AwsSecretException on AWS errors).
val dbPassword: String? = awsSecrets.getOrNull(dbPasswordNeed)

// Store or update a value (creates if absent, updates if present).
awsSecrets.set(dbPasswordNeed, "new-password")
```

Secrets are stored as JSON-serialized strings in Secrets Manager.  The IAM role or
profile must have `secretsmanager:GetSecretValue`, `secretsmanager:CreateSecret`, and
`secretsmanager:UpdateSecret` permissions.

### ManySecretSources

Chain sources so that missing secrets fall through to the next source in line, with
an interactive prompt as the final fallback:

```kotlin
// Illustrative — tries environment vars first, then an encrypted file.
val secrets = ManySecretSources(
    EnvironmentSecretSource,
    EncryptedFileSecretSource("production"),
)

// get() tries each source in order; if all return null, prompts the user interactively.
val apiKey = secrets.get(myApiKeyNeed)
```

## Global Built-In Settings

Every Lightning Server application automatically includes a small set of global
settings.  You do not declare these yourself; they are registered by the framework
and will appear in `settings.json` automatically.

### `secretBasis` — Master Cryptographic Secret

```kotlin
// From globalSettings.kt
public val secretBasis: ServerSetting.Direct<SecretBasis> =
    ServerSetting("secretBasis", SecretBasis(), SecretBasis.serializer())
```

`SecretBasis` is a 512-bit master secret used throughout the framework for signing
session tokens, upload URLs, and other HMAC operations.  It is auto-generated on first
run and stored in `settings.json`.  **Do not commit `settings.json` to version control**;
the `SecretBasis` is equivalent to a private key.

> **Warning:** Changing `secretBasis` in production invalidates all existing signed
> tokens, active user sessions, and `future:` upload URLs.  Only rotate it during
> initial setup or a controlled migration.

Access it anywhere inside a handler:

```kotlin
// Illustrative
val cipher = secretBasis().cipher("my-purpose")
```

### `general` — Public URL and Project Name

```kotlin
// GeneralServerSettings defaults
data class GeneralServerSettings(
    val projectName: String = "My Project",
    val publicUrl: String = "http://localhost:8080",
    val wsUrl: String = ...,   // derived from publicUrl
    val debug: Boolean = false,
    val emergencyContact: String? = null,
)
```

`publicUrl` is the base URL where your server is reachable.  Many parts of the
framework use it when constructing absolute URLs (email magic links, OAuth redirects,
WebSocket addresses).  Set it to your real domain before going to production.

`debug = true` relaxes CORS restrictions to `*` — useful in development, never in
production.

Access it in a handler:

```kotlin
// Illustrative
val baseUrl = generalSettings().publicUrl
```

### `logging` and `telemetry`

`loggingSettings` controls log levels and output format.  `telemetrySettings` configures
OpenTelemetry export for distributed tracing and metrics.  Both have sensible no-op
defaults that require no configuration for local development.

## Settings in Tests

The `settings` lambda of `ServerBuilder.testBlocking { }` (or `test { }`) runs in a
`ServerSettings` context before the runtime starts, letting you override any declared
setting:

```kotlin
// Illustrative — overrides the cache and webUrl for a test.
fun myTest() = Server.testBlocking(settings = {
    Server.cache set Cache.Settings("ram")
    Server.webUrl set "http://test-host"
}) {
    // handlers here use the overridden values
}
```

Use `setStatic` to inject a fully-constructed service instance directly, bypassing
the URL-to-service transformation:

```kotlin
// Illustrative — injects a mock database without going through Database.Settings.
fun myTestWithMock() = Server.testBlocking(settings = {
    Server.database setStatic myMockDatabase
}) {
    // ...
}
```

Each `testBlocking` call creates a fresh runtime; settings set in one test cannot leak
into another.
