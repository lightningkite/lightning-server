# Deploy to AWS EC2 with Auto Scaling

Last updated December 2024 (`version-5`)

Lightning Server can automatically generate Terraform configuration to deploy your application to AWS EC2 with Auto Scaling and Application Load Balancing. This provides a traditional VM-based deployment as an alternative to serverless Lambda deployment.

## When to Use EC2 vs Lambda

| Consideration | EC2 | Lambda |
|---------------|-----|--------|
| Cold starts | None | Can be significant |
| Long-running tasks | Supported | 15-minute limit |
| Predictable traffic | More cost-effective | Pay per invocation |
| WebSockets | Full support | Limited |
| Memory/CPU | Full control | Up to 10GB RAM |
| Scaling speed | Minutes | Seconds |

**Choose EC2 when you need**: No cold starts, long-running processes, WebSocket connections, or predictable high traffic.

**Choose Lambda when you need**: Zero infrastructure management, pay-per-use billing, or automatic scaling for variable traffic.

## Prerequisites

1. **AWS Account**: With appropriate permissions for EC2, VPC, ALB, SQS, etc.
2. **Terraform**: Install Terraform CLI (https://www.terraform.io/downloads)
3. **AWS CLI**: Install and configure with your credentials
4. **Domain**: A domain managed in Route53 (required for HTTPS)
5. **S3 Bucket**: For Terraform state storage

## Step 1: Add EC2 Deployment Dependencies

```kotlin
// build.gradle.kts
dependencies {
    implementation("com.lightningkite.lightningserver:deploy-aws-ec2:$lightningServerVersion")

    // You also need an engine for local development
    implementation("com.lightningkite.lightningserver:engine-ktor:$lightningServerVersion")
    // OR engine-netty, engine-jdk-server

    // Add service implementations you'll use
    implementation("com.lightningkite.services:database-mongodb:$servicesVersion")
    implementation("com.lightningkite.services:cache-dynamodb:$servicesVersion")
    implementation("com.lightningkite.services:files-s3:$servicesVersion")
}
```

## Step 2: Create a Main Class for Your Server

Create an entry point that the EC2 instances will run:

```kotlin
// src/main/kotlin/Main.kt
import com.lightningkite.lightningserver.engine.ktor.KtorEngine
import com.lightningkite.lightningserver.sqs.SqsScheduleHandler
import io.ktor.server.netty.Netty
import java.io.File

object Main {
    @JvmStatic
    fun main(args: Array<String>) {
        val server = Server.build()
        val engine = KtorEngine(server)

        // Load settings from file (generated by Terraform)
        val settingsFile = System.getenv("SETTINGS_FILE") ?: "settings.json"
        engine.settings.loadFromFile(File(settingsFile))

        // Start SQS handler for scheduled tasks (if configured)
        System.getenv("SQS_SCHEDULE_QUEUE_URL")?.let { queueUrl ->
            SqsScheduleHandler(
                queueUrl = queueUrl,
                runtime = engine
            ).start()
        }

        // Start HTTP server on port 8080 (ALB forwards to this)
        engine.start(Netty, port = 8080)
    }
}
```

## Step 3: Create a Deployment Configuration

```kotlin
// src/main/kotlin/deploy/ProductionEc2.kt
import com.lightningkite.lightningserver.terraform.awsec2.*
import com.lightningkite.lightningserver.terraform.generated
import com.lightningkite.services.database.mongodb.mongodbAtlasFree
import com.lightningkite.services.cache.dynamodb.awsDynamoDb
import com.lightningkite.services.files.s3.awsS3Bucket
import com.lightningkite.toEmailAddress
import software.amazon.awssdk.regions.Region

object ProductionEc2 : TerraformAwsEc2Builder<Server>(Server) {
    // Required: AWS Configuration
    override val region = Region.US_WEST_2
    override val storageBucket = "your-terraform-state-bucket"

    // Required: Domain Configuration
    override val domainZone = "yourapp.com"
    override val domain = "api.yourapp.com"

    // Required: Application Configuration
    override val mainClass = Main::class
    override val displayName = "YourApp Production"
    override val debug = false
    override val emergencyContact = "ops@yourapp.com".toEmailAddress()

    // Optional: Instance Configuration (defaults shown)
    // override val instanceType = "t4g.medium"  // ARM/Graviton by default
    // override val minInstances = 1
    // override val maxInstances = 4
    // override val desiredInstances = 2

    // Optional: Health Check Configuration
    // override val healthCheckPath = "/meta/online"

    // Configure services
    override fun Server.settings() {
        database.mongodbAtlasFree(
            orgId = "your-mongodb-org-id",
            zoneName = "Zone 1"
        )
        cache.awsDynamoDb()
        files.awsS3Bucket()
        secretBasis.generated()
    }
}

// Entry point for deployment
object ProductionEc2Deploy {
    @JvmStatic
    fun main(vararg args: String) = ProductionEc2.deploy()
}
```

## Step 4: Build Your Application JAR

The deployment uses a shadow/fat JAR containing all dependencies:

```kotlin
// build.gradle.kts
plugins {
    id("com.github.johnrengelman.shadow") version "8.1.1"
}

tasks.shadowJar {
    archiveClassifier.set("all")
    manifest {
        attributes["Main-Class"] = "com.yourapp.Main"
    }
}
```

Build the JAR:

```bash
./gradlew shadowJar
```

## Step 5: Generate and Deploy

```bash
# Generate Terraform configuration
./gradlew run --args="ProductionEc2Deploy"

# Initialize and apply Terraform
cd terraform/yourapp-production
terraform init
terraform plan
terraform apply
```

## What Gets Created

The deployment creates:

- **VPC**: With public/private subnets across 3 availability zones
- **Application Load Balancer**: HTTPS termination with TLS 1.3
- **Auto Scaling Group**: With target tracking on CPU utilization
- **Launch Template**: Amazon Linux 2023 with Corretto 17
- **SQS Queue**: For distributed scheduled task execution
- **EventBridge Rules**: For each scheduled task in your server
- **CloudWatch**: Log groups, alarms, and metrics
- **IAM Roles**: Least-privilege access for EC2 instances
- **Route53**: DNS records pointing to the ALB
- **ACM Certificate**: Automatically validated via DNS

## Scheduled Tasks

Scheduled tasks are distributed across EC2 instances via SQS. When you define schedules in your server:

```kotlin
object Server : ServerBuilder() {
    val dailyCleanup = schedule("dailyCleanup", Schedule.Daily(LocalTime(3, 0))) {
        // This runs on exactly one EC2 instance
        cleanupOldData()
    }

    val heartbeat = schedule("heartbeat", Schedule.Frequency(5.minutes)) {
        // Runs every 5 minutes, distributed across instances
        checkHealth()
    }
}
```

EventBridge rules trigger SQS messages, and the `SqsScheduleHandler` on each instance processes them. SQS visibility timeout ensures each task runs on exactly one instance.

## Updating Deployments

To update your deployed application:

```bash
# 1. Build new JAR
./gradlew shadowJar

# 2. Regenerate Terraform (uploads new JAR to S3)
./gradlew run --args="ProductionEc2Deploy"

# 3. Apply changes (triggers rolling update)
cd terraform/yourapp-production
terraform apply
```

The Auto Scaling Group performs a rolling update, replacing instances one at a time while maintaining availability.

## Cost Optimization

1. **Use Graviton instances**: 20-40% cheaper than equivalent x86
2. **Right-size instances**: Start small, scale based on metrics
3. **Single NAT gateway**: Default saves ~$30-45/mo (see note in code about HA)
4. **Spot instances**: For non-production (requires additional configuration)

## Troubleshooting

### Instances Keep Getting Replaced

If the ASG continuously terminates and launches instances:
1. Check `healthCheckPath` returns HTTP 200
2. Verify the endpoint responds within `healthCheckTimeout`
3. Check CloudWatch logs for application startup errors
4. Ensure `healthCheckGracePeriod` is long enough for your app to start

### Application Won't Start

Check the user-data log:
```bash
aws ssm start-session --target i-xxxxxxxxxxxxx
sudo cat /var/log/user-data.log
sudo journalctl -u lightning-server
```

### SQS Messages Not Processing

1. Verify `SQS_SCHEDULE_QUEUE_URL` environment variable is set
2. Check IAM permissions for SQS access
3. Look for errors in application logs

### S3 Download Failures

The user-data script retries S3 downloads with exponential backoff. If downloads still fail:
1. Check IAM role has `s3:GetObject` permission
2. Verify the deployment bucket exists
3. Check VPC has internet access (NAT gateway)

## Security Features

- **IMDSv2 required**: Prevents SSRF attacks on instance metadata
- **Private subnets**: Instances not directly accessible from internet
- **Encrypted EBS**: Root volumes encrypted at rest
- **Encrypted S3**: Deployment bucket uses AES-256 encryption
- **Encrypted settings**: Settings file encrypted with PBKDF2 + AES-256
- **Restricted permissions**: Settings file is chmod 600
- **Security groups**: EC2 only accepts traffic from ALB
