# Lightning Kite Stack — Release Readiness Plan

**Target:** a credible, advertised **public beta → 1.0** of the full stack
(service-abstractions, lightning-server, kiteui, lightning-server-kiteui, ls-kiteui-starter).

**Framing:** the architecture is strong; the gap is *productization*. The single hardest part
historically — excellent documentation — becomes economical only if examples are **self-verifying**
(compiled + tested in CI), so they can't silently rot the way the ones we just cleaned up did.

**Division of labor:**
- 🤖 = Claude can carry this out end-to-end (generate + verify + iterate).
- 👤 = needs a human (accounts/keys, product decisions, final voice/positioning sign-off).
- 🤝 = Claude does the work, human makes a gating decision.

---

## Workstream A — The verified documentation system (the crux) 🤖

This is what makes the rest practical. Build once, then content is cheap and drift-proof.

- **A1. Example-verification harness (kotlinx-knit).** Markdown code blocks are extracted, compiled
  against a real module, and run as tests. A broken example *fails CI*. (POC in progress.)
- **A2. API reference (Dokka).** Generate HTML API docs from KDoc for every published module.
  Surfaces KDoc gaps as a measurable coverage number.
- **A3. Static docs site.** One site aggregating guides + API ref + tutorials (e.g. MkDocs Material
  or Writerside). Versioned, searchable, deploys from CI.
- **A4. CI gate.** `docs build + knit test + dokka` run on every PR. Docs cannot merge broken.
- **Outcome:** the cost of "keep docs correct forever" drops to ~zero; the cost of "write more docs"
  drops to review time.

## Workstream B — Build & publish hygiene 🤝

- **B1. Builds green from a clean clone.** Remove the combo's `-local` LS pin; everything builds with
  `git clone && ./gradlew build`. (Hard blocker for any external eyeballs.) 🤖
- **B2. Maven Central publishing.** Signed artifacts, proper coordinates, on Central (not the private
  S3 maven). 👤 for the Sonatype account + GPG keys; 🤖 for the Gradle publishing config.
- **B3. Semantic versioning + deprecation policy.** Written policy; CI/API-check to catch breaks
  (you already have API contract tests in LS — extend the pattern). 🤝
- **B4. Cross-library compatibility matrix.** A machine- and human-readable table: which LS ↔ combo ↔
  kiteui ↔ starter versions work together, kept current by CI. 🤖

## Workstream C — Documentation content 🤖

- **C2. Concept guides** — the mental models (ServerBuilder/definition, settings/runtime, typed

## Phasing

| Phase | Contents | Exit criteria |
|---|---|---|
| **0. Prove it** | A1 harness + one verified chapter (POC) | You judge quality "good enough." |
| **1. Foundations** | A1–A4, B1, C5 (READMEs), C6 start | Docs site builds in CI; clean-clone builds; API ref live. |
| **2. Content** | C1–C4, C7, B4, E2 | A new dev can go zero→deployed app from docs alone. |
| **3. Publish** | B2, B3, F1–F2 | On Maven Central, semver'd, contributable. |
| **4. Full-stack** | D1–D2, E1, F4, G1 | KiteUI unbroken; full-stack tutorial works end-to-end. |
| **5. Public beta** | G2, G3 | Advertised beta out; feedback loop open. |
| **6. → 1.0** | hardening, stability guarantees | Production-commitment messaging. |

## Risks / honest notes
- **Full-stack scope is blocked on D (kiteui migration).** Phases 1–3 can proceed on the backend in
  parallel; the *advertised full-stack launch* waits on D.
- **The two bleeding-edge-Kotlin bets** (context params, internal serialization) are accepted risk
  per your call (adapt/fork). For external trust, shield them behind a stable public surface and say
  so in the versioning policy — don't hide it.
- **Effort calibration:** the POC tells us the real per-chapter cost. If a verified chapter takes me
  ~X to produce at quality, C1–C4 is a known multiple of X — we can then decide pace.

## Documentation Site (MkDocs Material)

The site is configured at `mkdocs.yml` in the repo root and sources content
from `docs-guide/guide/` (the eight verified chapters plus `index.md`).

### Install

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install mkdocs-material
```

### Build (static HTML → `site/`)

```bash
mkdocs build
```

Output lands in `site/`.  The directory is git-ignored.

### Local preview

```bash
mkdocs serve
# open http://127.0.0.1:8000
```

### API Reference (Dokka)

Dokka V2 is already configured per-module.  Generate HTML API docs:

```bash
# Single module
./gradlew :core:dokkaGenerateHtml
# Output: core/build/dokka/html/

# All modules (run per module; there is no multi-module aggregate task yet)
./gradlew dokkaGenerateHtml
```

To surface Dokka output inside the MkDocs site, copy it into `site/api/` after
building:

```bash
mkdocs build
mkdir -p site/api
cp -r core/build/dokka/html/ site/api/
```

The `mkdocs.yml` nav already references `api/index.html` so the sidebar link
works once Dokka output is present.

### GitHub Pages CI sketch

```yaml
# .github/workflows/docs.yml
name: Docs

on:
  push:
    branches: [master]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.x'

      - run: pip install mkdocs-material

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - name: Build Dokka API reference
        run: ./gradlew dokkaGenerateHtml

      - name: Build MkDocs site
        run: mkdocs build

      - name: Copy Dokka output into site/api/
        run: |
          mkdir -p site/api
          # Aggregate per-module HTML under site/api/<module>/
          for dir in */build/dokka/html; do
            module=$(echo $dir | cut -d/ -f1)
            cp -r "$dir" "site/api/$module"
          done

      - name: Deploy to GitHub Pages
        run: mkdocs gh-deploy --force
```
